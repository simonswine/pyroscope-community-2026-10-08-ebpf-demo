01 / THE ORIGIN STORY

It started with packets.
It didn’t stop there.

A packet filter evolved into a programmable foundation for networking, security, and observability.

1992

Berkeley Packet Filter

Classic BPF arrives as an efficient way to filter network packets. A tiny virtual machine decides which packets to keep without copying everything to user space.

THE ORIGINAL BPF
2014

Beyond packet filtering

Linux 3.18 introduces the bpf() syscall. More registers, maps, and a richer execution model lay the groundwork for general-purpose kernel instrumentation.

EXTENDED BPF
Today

A platform for insight

eBPF programs attach to many types of events. Tools use them to observe systems, enforce policies, and build continuous profilers without patching the kernel.

NETWORKING · SECURITY · PROFILING
↳

Before “extended”: a deliberately tiny packet machine.

The original Berkeley Packet Filter was described by Steven McCanne and Van Jacobson in 1992, with the paper published in 1993. Tools such as tcpdump could ask the kernel to evaluate a filter before copying packets to user space. Classic BPF used an accumulator, an index register, a small scratch-memory area, and a compact instruction set. A filter returned how many bytes of a packet to capture—or zero to discard it. Its restricted control flow made execution predictable; it wasn’t a general-purpose kernel extension.

THE INSTRUCTION SET

A bigger virtual machine

Extended BPF replaced the classic accumulator model with eleven 64-bit registers, a richer instruction set, and a 512-byte stack. Its calling convention maps more naturally to modern CPUs, supporting efficient native-code JIT compilation. This was a new execution model, not simply more packet-filter rules.

THE SAFETY & DATA MODEL

Useful, but constrained

A more capable verifier tracks register and pointer states and checks memory access and execution bounds. Controlled helper calls expose kernel functionality, while persistent BPF maps hold state and connect programs to user space. Early eBPF still prohibited loops; support for bounded loops came much later, in Linux 5.3.

THE LINUX ROLLOUT

Not one overnight switch

Linux 3.18 added the bpf() system call, providing a user-space API for loading programs and managing maps. Tracing and other attachment mechanisms expanded over subsequent releases. These pieces made BPF useful far beyond packet capture.

“eBPF” means extended Berkeley Packet Filter; there is no certification checklist for the name. The distinction began with the extended virtual machine. Today, people often say “BPF” when they mean the modern eBPF platform. JIT compilation alone isn’t the distinction—classic BPF can be JIT-compiled too.

03 / FROM EVENTS TO ANSWERS

Where does your
workload spend its time?

The OpenTelemetry eBPF profiler samples running workloads and reconstructs call stacks, turning scattered observations into a picture of CPU activity.

The profiling pipeline

  1. 1

    Trigger a sample

    Linux perf events periodically invoke an eBPF sampling program on CPUs. Sampling avoids tracing every function call.

  2. 2

    Capture & unwind stacks

    The program records thread context and unwinds stacks using runtime-specific support and metadata supplied by the user-space agent. Native and supported managed runtimes need different techniques.

  3. 3

    Resolve & enrich

    The agent processes stack traces, resolves code locations to symbols, and associates samples with process and available workload metadata.

  4. 4

    Export profiles

    Aggregated profiles travel over OTLP to a compatible Collector or profiling backend, where you can explore hot paths over time.

04 / GO MEETS THE KERNEL

Two programs.
Two different worlds.

The OTel eBPF profiler has a Go user-space agent and C eBPF programs. Go orchestrates them; it does not run inside the kernel.

BUILD TIME

C → eBPF object

Clang/LLVM compiles the kernel-side C code into an ELF object containing BPF instructions and map definitions. The Go compiler builds the agent separately. Generated bindings or embedded objects can package the two together.

# Conceptual build pipeline, not the OTel build command
clang -O2 -g -target bpf -c program.bpf.c -o program.bpf.o
# Then build the user-space agent with the Go toolchain.

This assumes suitable headers, includes, and target settings. Real profiler builds handle these through their build tooling. Go’s normal compiler does not produce eBPF bytecode.

LOAD TIME

Go → Linux BPF API

A Go loader, using a library such as cilium/ebpf, reads the object and creates maps and programs through the bpf() system call. The kernel verifies the program before accepting it. The agent attaches it to an event source; CPU profiling also uses Linux perf-event APIs.

For a generic Go project, bpf2go can invoke Clang and generate Go bindings. This is a common pattern, not a claim that the OTel profiler uses that exact build workflow.

RUN TIME

Maps & buffers, not HTTP

The Go agent updates BPF maps with configuration and unwinding metadata. The eBPF program reads those maps when samples arrive, and writes stack data and identifiers into maps or event buffers.

The agent reads results via map operations or perf/ring-buffer readers, resolves symbols, aggregates samples, and exports profiles. Kernel/user-space communication uses kernel APIs and shared buffers—not a Go function call into C on every sample.

↔

Separate lifetimes, explicit handles.

Go owns file descriptors for programs, maps, and attachments. The agent must manage their lifetime and close resources on shutdown; pinned resources can outlive a process. The eBPF code has no Go garbage collector or Go runtime.

05 / TRY IT ON LINUX

From explanation
to observation.

Three small bpftrace experiments for your own test process. bpftrace compiles its tracing language to eBPF; it is not the OTel profiler.

Before you start

Use a Linux test machine where you have permission to trace. Install Go and bpftrace with your distribution’s package manager (Ubuntu/Debian: sudo apt install bpftrace). These examples require kernel tracing support and sufficient privileges; containers and locked-down kernels may restrict it. Don’t disable security controls to make them work.

All three labs use the included Go workload: examples/workload.go. It hashes a 1 MB buffer, prints hello world, then sleeps for 500 ms. Build a real binary rather than using go run, so the printed PID and uprobe target refer to the workload itself. Leave it running in Terminal A. In Terminal B, run the one-shot discovery command below and export its result as WORKLOAD_PID. The write and stack examples reuse it—no /proc scan or process-name matching. The uprobe example needs no PID or discovery.

go build -o examples/workload examples/workload.go
./examples/workload

Terminal B · discover once: run only one instance of the workload. This uprobe captures the kernel PID on its next helloWorld() call and exits. The result is stored in your current shell’s environment, not Terminal A’s.

export WORKLOAD_PID="$(sudo bpftrace -q examples/discover.bt)"
# Must contain exactly one positive integer before running the examples:
[[ "$WORKLOAD_PID" =~ ^[1-9][0-9]*$ ]] && echo "Discovered: $WORKLOAD_PID"

If discovery returns empty output or an error, stop here and check the workload and tracing support. It times out after ten seconds. Run discovery again whenever you restart the workload; kernel PIDs can be reused. Inside the privileged container, omit sudo.

The complete Go workload · examples/workload.go

//go:noinline preserves the function for the uprobe. The global result retains the hash, and the write supplies an event for the syscall example. The flags let the same binary run continuously or stop after a fixed number of calls.

package main

import (
    "crypto/sha256"
    "flag"
    "fmt"
    "os"
    "time"
)

var result [32]byte

//go:noinline
func doWork(data []byte) [32]byte {
    return sha256.Sum256(data)
}

//go:noinline
func helloWorld() error {
    _, err := fmt.Fprintln(os.Stdout, "hello world")
    return err
}

func main() {
    iterations := flag.Int("iterations", 0, "number of calls; 0 runs until interrupted")
    pause := flag.Duration("pause", 500*time.Millisecond, "delay between calls")
    flag.Parse()
    if *iterations < 0 || *pause < 0 {
        fmt.Fprintln(os.Stderr, "iterations and pause must be nonnegative")
        os.Exit(1)
    }
    fmt.Println("PID:", os.Getpid())
    data := make([]byte, 1_000_000)
    for i := 0; *iterations == 0 || i < *iterations; i++ {
        result = doWork(data)
        if err := helloWorld(); err != nil {
            fmt.Fprintln(os.Stderr, err)
            os.Exit(1)
        }
        time.Sleep(*pause)
    }
}

DOCKER WALKTHROUGH / LINUX HOST

An eBPF playground, step by step

A plain docker run --name ebpf-playground -t -i golang:latest provides Go, but not the permissions and tracing filesystem needed for these probes. Below is an expanded demo command. Use a disposable, trusted Linux test machine: --privileged grants broad host access, so this is not an appropriate default for production or untrusted workloads. Host PID sharing is not needed for these updated probes.

1. On the Linux host: start in this project’s root directory.

docker run --name ebpf-playground -t -i \
  --privileged \
  -v "$PWD":/workspace \
  -v /sys/kernel/tracing:/sys/kernel/tracing:ro \
  -w /workspace \
  golang:latest bash

2. Terminal A · demo: inside the container, install the tools and run the Go workload in the foreground. Leave this session running.

apt-get update && apt-get install -y bpftrace
bpftrace --version
go version
go build -o examples/workload examples/workload.go
./examples/workload

3. Terminal B · tracing: open another host terminal and enter the same container. Discover the kernel PID once and keep it in this shell’s environment. The write and stack examples reuse it; the uprobe is scoped directly to the executable and needs no PID. Both sessions must see the same executable file, and exactly one workload instance should be running. Don’t rebuild it while running.

docker exec -t -i -w /workspace ebpf-playground bash

export WORKLOAD_PID="$(bpftrace -q examples/discover.bt)"
[[ "$WORKLOAD_PID" =~ ^[1-9][0-9]*$ ]] && echo "Discovered: $WORKLOAD_PID"
# Stop here if discovery did not return one positive integer.
# Each probe runs for ten seconds while Terminal A keeps running:
bpftrace examples/writes.bt "$WORKLOAD_PID"
bpftrace examples/stacks.bt "$WORKLOAD_PID"
bpftrace examples/uprobe.bt

Expected results: writes and stacks from the Go demo, plus eBPF observed: helloWorld() called in Terminal B each time the demo calls main.helloWorld. Terminal A continues printing hello world. The uprobe also counts entries during its ten-second window. The count depends on how many iterations occur while attached.

4. Cleanup: exit Terminal B, press Ctrl+C in Terminal A to stop the workload, then exit its shell. Back on the host, remove the stopped demo container. The bind-mounted source files and compiled binary stay in your project directory; the container-installed packages do not.

docker rm ebpf-playground
# Optional: remove the generated binary
rm -f examples/workload

Host requirements still apply: Docker shares the host kernel; it doesn’t supply eBPF support or bypass kernel lockdown. This walkthrough assumes rootful Docker on native Linux and a Debian-based golang:latest image. Rootless Docker may not support the required access. Docker Desktop on macOS/Windows runs against its Linux VM, not the desktop’s kernel, and these host mount instructions do not apply there. latest is convenient for a demo but changes over time; pin a tested image version for repeatability. Don’t disable security controls if tracing is denied.

EXAMPLE 01 / EVENT COUNTING

Count write system calls

Keep the demo running in Terminal A. Reuse WORKLOAD_PID from the discovery step. This counts write calls without reading their contents.

sudo bpftrace examples/writes.bt "$WORKLOAD_PID"

What to expect: a count printed at exit: the workload prints hello world on each iteration. No application data is captured. Only the discovered process is counted.

What it teaches: a hook runs on an event, a predicate filters it, and a BPF map aggregates a result. This counts syscall invocations, not bytes or CPU time.

EXAMPLE 02 / STACK SAMPLING

Sample user-space stacks

Run against the already-running Go workload using the discovered WORKLOAD_PID. Sampling at 490 Hz provides more sampling opportunities, at higher overhead than 49 Hz.

sudo bpftrace examples/stacks.bt "$WORKLOAD_PID"

The script now only samples and filters—discovery was done once:

profile:hz:490
/(uint64)curtask->tgid == $1/
{
    @stacks[ustack(20)] = count();
}
interval:s:10 { exit(); }

What to expect: stack traces with sample counts. Sleeping threads aren’t sampled as running on the CPU. With a 500 ms pause and a short hashing operation, CPU samples may be very sparse or empty. For the stack-sampling experiment, restart the workload with ./examples/workload -pause 0 to keep it CPU-active (this also prints rapidly). Run discovery again after restarting, then repeat the stack example; use Ctrl+C to stop the workload.

What it teaches: recurring samples build a distribution of observed stacks. Native stack quality depends on unwind support, frame pointers, architecture, and symbols. Go’s goroutine stacks and runtime transitions can produce incomplete stacks with generic bpftrace unwinding. Keep Go symbols (don’t build with -ldflags='-s -w'). These are native stack samples, not OTel’s runtime-aware unwinding.

EXAMPLE 03 / USER-SPACE FUNCTION PROBE

Observe a function with a uprobe

A tracepoint observes a kernel event. A uprobe attaches to an instruction in a user-space executable—here, the entry to main.helloWorld in the same Go workload. Unlike sampling, this fires on every invocation of that function.

The workload prints through this named function. Inlining is disabled so the probe has a stable function entry to attach to:

//go:noinline
func helloWorld() error {
    _, err := fmt.Fprintln(os.Stdout, "hello world")
    return err
}

Keep the Go workload running in Terminal A. In Terminal B, attach directly to the executable—no PID or discovery step is needed. This observes all running instances of this exact executable file.

sudo bpftrace examples/uprobe.bt

Inside the privileged demo container, omit sudo. The executable path and function name scope the uprobe:

uprobe:./examples/workload:main.helloWorld
{
    printf("eBPF observed: helloWorld() called\n");
    @calls = count();
}
interval:s:10 { exit(); }

What to expect: Terminal A prints hello world roughly every 500 ms. For each function entry while attached, Terminal B prints eBPF observed: helloWorld() called. This observes the function entry, not the string’s contents or whether the subsequent write succeeds. After ten seconds, bpftrace exits and reports the call count, while the demo keeps running. The probe emits its own message—it does not replace, intercept, or modify the Go program’s stdout. bpftrace output may be buffered; the count is invocations, not duration.

How it works: the kernel manages the user-space probe and invokes the eBPF handler when the Go function entry is reached. No Go source instrumentation or Go eBPF library is needed to attach externally.

The Go ABI matters: we deliberately don’t use arg0. Modern Go uses an internal register calling convention that differs from C, and slices span multiple values. Reading arguments requires knowledge of the specific Go version and architecture; C-style argument examples aren’t portable to Go.

Practical limits: preserve symbols and the //go:noinline directive; a wrong path or stripped binary can prevent attachment. High-frequency uprobes can have noticeable overhead. Don’t naively add a uretprobe to Go functions: return-address rewriting can conflict with Go’s stack management. Entry-only counting avoids that issue.

!

A teaching tool, not a replacement for the profiler.

These examples do not reproduce OTel’s runtime-aware unwinding, workload metadata, or OTLP export. PID filters limit recorded data, but hooks may still fire more broadly. Keep experiments short, expect some overhead, and stop tracing with Ctrl+C. Stop the continuously running Go workload with Ctrl+C in its terminal too; all three traces stop after ten seconds without stopping the workload.

QUICK REFERENCE / KERNEL TRACEPOINTS

Other useful places to observe Linux

Tracepoints are named instrumentation sites in the kernel. Use the tracepoint: provider in bpftrace; their fields are exposed through args. Availability and field layouts depend on your kernel—inspect them before writing a script.

Common tracepoints and what they tell you
ProbeUseful forWhat to watch out for
tracepoint:syscalls:sys_enter_read
tracepoint:syscalls:sys_enter_write		Count application I/O requests; inspect file descriptors and requested byte counts.Entry counts are requests, not successful transfers. Exit events expose the return value; negative values indicate errors.
tracepoint:syscalls:sys_enter_openat
tracepoint:syscalls:sys_exit_openat		Understand file-open activity and failures.Some applications use openat2 instead. Paths can contain sensitive information—avoid collecting them unnecessarily.
tracepoint:sched:sched_switchObserve context switches and build off-CPU analyses.The event describes outgoing and incoming threads. Filter using fields such as args.prev_pid and args.next_pid, not just the current task. Off-CPU time is not automatically CPU contention.
tracepoint:sched:sched_wakeup
tracepoint:sched:sched_wakeup_new		Study when threads become runnable; correlate with switches to investigate scheduling delay.The current task is often the waker, not the thread being awakened. args.pid identifies the target thread.
tracepoint:sched:sched_process_exec
tracepoint:sched:sched_process_exit		Track executable changes and task lifetimes.Exit events occur for threads too. Linux tracepoint PIDs commonly identify tasks (thread IDs), not necessarily whole processes.
tracepoint:block:block_rq_issue
tracepoint:block:block_rq_complete		Investigate block-device requests, throughput, and completion behavior.Completion may run in interrupt or worker context. Filtering by the current process can misattribute I/O, and pairing requests correctly requires care.
tracepoint:net:net_dev_queue
tracepoint:net:netif_receive_skb		Explore packet activity through network devices.Packet events do not reliably identify the owning application. Aggregation, offloads, and kernel context affect interpretation.
tracepoint:tcp:tcp_retransmit_skbInvestigate TCP retransmission activity.A retransmission is a symptom, not a diagnosis. Counting events does not directly measure packet loss or uniquely identify a workload.

Discover what your machine actually supports

# List probes; these commands do not start tracing.
bpftrace -l 'tracepoint:syscalls:sys_*write*'
bpftrace -l 'tracepoint:sched:*'
bpftrace -l 'tracepoint:block:*'
bpftrace -l 'tracepoint:net:*'
bpftrace -l 'tracepoint:tcp:*'

# Show the fields available as args for a particular event.
bpftrace -lv 'tracepoint:syscalls:sys_enter_write'
bpftrace -lv 'tracepoint:sched:sched_switch'

Not everything is a tracepoint: profile:hz:490 is periodic perf-event sampling; uprobe:... observes user-space instructions; kprobe:... observes kernel function entries. Function probes can be more sensitive to implementation changes than named tracepoints. interval:s:10 is a timed trigger, which our examples use to stop the experiment.

Keep probes short and scope recorded data to your test workload where the event semantics allow it. Scheduler, storage, and network events often require more careful attribution than a simple current-PID filter.
